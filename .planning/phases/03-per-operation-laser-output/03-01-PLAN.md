  <action>
    New module crates/lasercraft-core/src/resolve.rs (pure, no I/O, no unwrap/panic — the crate denies them): define `OperationBlock { operation: Operation, toolpaths: Vec<Toolpath> }` and `fn resolve_job(job: &JobFile) -> Result<Vec<OperationBlock>, ResolveError>`. Resolve in persisted order: iterate job.operations in Vec order (never a map); for each operation, collect toolpaths bound to it via job.bindings — a binding binds a Selector to an operation id; match toolpaths by their `source` field against `Selector::Node(id)` (and Layer/Swatch selectors resolve against matching toolpath source strings); preserve toolpath order as stored. Stamp each resolved toolpath with its operation's feed/power into the toolpath-level `feed`/`power` fields (the emitter already honors these) so emit needs minimal change. Toolpaths whose source matches no binding are dropped (OUT-05). A binding referencing an unknown operation id returns `Err(ResolveError::UnknownOperation)` — calm error, never panic. An operation with zero bound toolpaths yields an empty block and is skipped in output but does not error. Define `ResolveError` with Display impl. In emit.rs add `pub fn emit_job(job: &JobFile, profile: &MachineProfile) -> Result<String, EmitError>` as the canonical entry: it calls resolve_job, then iterates operation blocks in order, and for each block runs `for pass in 1..=operation.passes` over that block's toolpaths (operation-major nesting, clamping passes to MAX_PASSES), emitting a `; operation <id> (<kind>) pass <n>` comment line between blocks/passes for debuggability. Keep the existing `emit(&[Toolpath], profile, options)` signature and behavior unchanged for raw use; emit_job reuses the same header/footer/per-toolpath emission and the same num() float formatting. Re-export resolve types and emit_job from lib.rs. Add golden tests in crates/lasercraft-core/tests/emit.rs following the existing golden-bytes assert_eq! pattern: (a) a job with Cut(power 100, feed 300, passes 2), Engrave(power 30, feed 1200, passes 1), Score(power 10, feed 2000, passes 1) asserting each block carries its own S/F values and pass counts in operation order; (b) one shape bound to Engrave then Cut asserting two ordered blocks repeat the same geometry coordinates; (c) a job with one unbound toolpath asserting its coordinates are absent from output.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-3-01 | Tampering | resolve_job on hostile job files | high | mitigate | Dangling binding or unknown operation returns calm ResolveError; core denies unwrap/expect/panic; all points re-validated by existing emit validation |
| T-3-02 | Information Disclosure | G-code output | low | accept | Output contains only job geometry and machine params already in the input files |
| T-3-03 | Denial of Service | passes field | medium | mitigate | Operation.passes clamped to MAX_PASSES (10) before the pass loop, bounding output size on hostile jobs |
| T-3-SC | Tampering | cargo installs | low | accept | No new dependencies are added in this plan |

## Severity Scale

- critical: remote code execution or full corruption on untrusted input
- high: panic/abort or silent data loss on a malformed but plausible file
- medium: recoverable error surfaced incorrectly, or bounded resource amplification
- low: requires an already-compromised local environment
